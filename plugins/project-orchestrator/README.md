# 司南 · 项目流程总监

**把一个多专家项目串成一条线：开工立规矩，每个交接点给路线，收到东西先过闸。**

它不是第 8 个专家，它是那 7 个专家之间的接缝。

## 类型

Agent 型（单个 AI 专家）· maxTurns 80 · `12-IndustryConsultant`

## 它解决什么

一个人跑单点任务不会出问题。七个专家跑一个项目才会出问题，而且出的都不是“某一步做错了”，是四种接缝病：

| 病 | 真实症状 |
|---|---|
| **交接损耗** | 析纲说“表达方式”但没说“强调层级”，淬言要的正是强调层级。没人发现，靠用户临场补 |
| **验收失真** | 落版说“45 页全出、质量门通过”，真机一查发现 3 页是整页截图 |
| **分支无人判** | 验筹判「需重大修改」，流程该停吗？回筑策重做还是带病往前走？ |
| **版本灾难** | `v3_终稿_改_最终.pptx`。三个月后没人分得清哪版是准的 |

这四件没有一件是创作，全是流程管理。

## 三个身份

| 身份 | 出现时机 | 产出 |
|---|---|---|
| **立规者** | 项目开工 | 《项目章程》——一页纸，所有专家必须遵守的底线 |
| **引导者** | 每个交接点 | 《交接包》——去哪儿、带什么、别踩什么（复制粘贴即可用） |
| **监理者** | 收到交付物 | 《验收单》——过 / 有条件过 / 打回 + 台账更新 |

附带身份：**项目入口**。素材收集、甲方沟通、待补数据、图片到位——这类不属于任何专家的杂活归它记录跟进。

## 怎么用

它不是流水线，是**指挥台**。每次开工前先到它这里领三样东西：现在在第几步、带什么材料去找谁、哪些坑不能踩。

```
① 你 → 司南：「启动 <项目>」→ 它出章程草案 + 台账，等你批
② 你批 → 它出交接包：「去筑策，把这段贴过去」
③ 筑策产出 → 你回来贴给它 → 它过闸、更新台账
④ 它出下一个交接包 → 循环，直到交付
```

**用户是那个搬运的人。** 专家之间不共享上下文（环境约束），所以唯一能跨会话传递的东西是文件。好处是：每次搬运天然是一个检查点。

## 四条核心原则

1. **章程可加严，不可放松。** 与专家自身安全规则冲突时取更严的一条。不许用“项目特殊”当借口给纪律开口子。
2. **闸门只查门槛，不评优劣。** 评优劣就会开始替用户审美，然后和立象、琢磨打架。
3. **能判打回，不能代签通过。** 打回是保守动作（最坏多做一轮），放行是冒险动作（最坏赔上后面好几步）。
4. **无法核验 ≠ 通过。** 材料不全时诚实说“这条我核不了”，比假装过了有用。

## 七道闸

`筑策 → 验筹 → 析纲 → 淬言 → 立象 → 落版 → 琢磨 → 交付`，每两个相邻步骤之间一道，另加开工前的闸门零。

每道 3–5 条硬判据，完整表在 `skills/project-orchestration-toolkit/references/闸门判据表.md`。

## 它不做

| 不做 | 该找谁 |
|---|---|
| 不创作（策划 / 文案 / 设计 / 排版） | 对应专家 |
| 不替你签字（能判不合格，合格要你点头） | 用户 |
| 不改上游产物（发现问题走“退回”） | 上游专家 |
| 不评优劣（只查门槛） | 用户 |
| 不做内容判断（数字合不合理、句子好不好） | 验筹 / 淬言 |

有人让它“顺手写个摘要”，它的回答是：“这个归筑策/淬言，我把交接包给你，你去那边做，做完回来我过闸。”

```

    闸门判据表.md          七道闸全部判据 + 跳步时的加严规则
```

## 校验脚本

```bash
python scripts/check_project.py <项目目录>              # 只校验
python scripts/check_project.py <项目目录> --render     # 先由 json 生成 台账.md，再校验
```

查四件事：交付物是否真的存在、`台账.md` 与 `project.json` 是否一致、有没有步骤标了已通过却没有闸门结论或交付物、未闭环项与待办是否超期。

退出码：`0` 干净 / `1` 有问题 / `2` 读不了。

**它查不了“做得对不对”，只查“账实是否相符”。** 后者靠人记一定会漂。

## 使用示例

- 启动新项目：先出项目章程草案和台账给我看，我批完再开工。
- 筑策把报告交了，你过一下闸，然后告诉我下一步去哪、带什么。
- 现在项目卡在哪？把台账、未闭环项和超期待办一起给我。
