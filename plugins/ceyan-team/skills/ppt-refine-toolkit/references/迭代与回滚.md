# 迭代与回滚

> 精修的难点不在"改"，在"什么时候停"。
> 这份文件解决两件事：**怎么不把改坏的地方留下来**，**怎么知道该停了**。

---

## 一、轮次预算

| 场景 | 预算 | 说明 |
|---|---|---|
| 标准精修 | **1 轮** | 全篇扫一遍 + 修 + 复渲染一次 |
| 重点页深磨 | **2 轮** | 第 2 轮**必须用户明确说继续**才开 |
| 任何页 | **绝对上限 2 轮** | 第 3 轮一律拒绝，转 `needs_human` |

**为什么要卡死在 2 轮**：渲染成本每轮翻倍（每页都要重新渲染 PNG + 重新读规则 + 重新读 spec）。45 页两轮大概是 200–300K token 的量级，三轮就接近上下文上限，后期质量会断崖式下降。

更要紧的是——**改到第 3 轮通常说明问题不在手艺**，而是规则和内容本身打架。这时候继续改只是把矛盾挪个地方。

---

## 二、每轮做什么

### 第 1 轮（必做）

按固定顺序检测，**不要跳序**：

```
① 图片渲染健全性（PNG 存在、非空白、尺寸对）
② 结构类：H1 出界 → H2 溢出 → H7 页眉页脚
③ 碰撞类：H3 文字重叠 → H6 元素碰撞
④ 可读性：H4 对比度
⑤ 内容类：H8 图片坏 → H9 元素缺失
⑥ 软规则：S1–S10（明显才动）
```

顺序有道理：结构问题会掩盖其他问题——先修溢出，往往碰撞自己就没了。反过来先修碰撞，修完移动元素又溢出，白干。

### 第 2 轮（用户授权才做）

**不重扫全部**，只做两件：

1. **复验第 1 轮改过的元素**（改完真的好了吗）
2. **扫新增的硬伤**（改动有没有引入新问题）

**不碰第 1 轮已经判定为软问题而没改的东西。** 第 2 轮再去动软问题，就是在磨审美，不是在修缺陷。

## 三、回滚：什么时候必须退回去

这是整个流程里最容易被跳过、也最重要的一步。

### 三种必须回滚的情形

| 情形 | 判定 | 动作 |
|---|---|---|
| **修完引入了新硬伤** | 改 A 坏了 B | `cp` 备份回去，整页判 `needs_human` |
| **软规则震荡** | 第 2 轮又冒出新的软问题（说明两个修法在互相拉扯） | 停，整页判 `needs_human` |
| **改动后用户说"还不如原来"** | 动了设计意图 | 从备份回滚整页，重来只改硬伤 |

### 怎么回滚

```bash
cp "<project>/.review/backup/<page>.iter1.svg" "<project>/svg_output/<page>.svg"
```

回滚后**必须重新渲染**，确认回到原状再继续。不重渲染就往下走，等于在验一张过期图。

### 备份纪律（没有备份不许改）

```bash
# 每页第一次编辑前
mkdir -p "<project>/.review/backup"
cp "<project>/svg_output/<page>.svg" "<project>/.review/backup/<page>.iter1.svg"
```

备份路径写进每条 finding 记录。**这是回滚唯一靠得住的东西**——不要指望"我记得原来是什么样"，改到第 12 页你就不记得了。

## 四、终止条件

### 单页"过"的判定

四条全过：

```
硬伤 0 条
软问题 ≤ 1 条（且已记录到 untouched_concerns）
可编辑性合格
未引入新问题
```

### 单页"必须停"的判定

任一命中就停，不再尝试：

- 2 轮用完仍有硬伤
- 修法之间互相矛盾（修 A 必坏 B，修 B 必坏 A）
- 需要改 `spec_lock` / 令牌 / 品牌决策才能解决（→ 立象）
- 需要改文案或删内容才能解决（→ 淬言 / 析纲）
- 需要把内容并成图才能解决（**这条无论如何不许**，宁可留着不好看）

### 停下之后写什么

进《已知残留清单》，**必须写清"为什么修不动"**：

```
P31 · 硬伤 H2 文字溢出 · 修不动
原因：该页 6 条要点，每条 28–34 字，在 32pt 正文下容器只容得下 4 条。
      缩到 28pt 会越出字号阶梯（阶梯最低 32）；删条要改内容（属淬言）。
建议：由淬言压到 4 条，或由析纲拆成两页。
```

**"为什么修不动"比"哪里没修好"有用得多。** 后者只能让用户焦虑，前者能告诉他下一步找谁。

## 五、禁止的四种"过检查"

这四种做法都能让检查立刻变绿，也都是作弊：

| 做法 | 为什么禁止 |
|---|---|
| **删元素** | 元素是内容。删了检查当然过，但汇报时少了东西 |
| **把字号降到阶梯以下** | 一时过关，全篇字重体系就乱了，而且投影时看不清 |
| **把内容并成一张图** | 直接违反"完全可编辑"这条硬红线，那页从此改不动 |
| **把复杂图表换成简单图表** | 图表类型是立象定的，换了等于改设计 |

**判断标准**：这个修改，是让页面**真的变好**，还是让**检查看不见问题**？后者一律不做。

## 六、进度台账（边改边填）

不要等最后一起写报告——改到第 30 页你就忘了第 7 页改了什么。用这张表边改边填：

```markdown
| 页 | 轮 | 状态 | 硬伤 | 软问题 | 改动数 | 备注 |
|---|---|---|---|---|---|---|
| P01 | 1 | ok | 0 | 0 | 0 | 封面，无问题 |
| P03 | 1 | fixed | H2×1 | S4×1 | 2 | 标题右移 6px、正文 15→16pt |
| P07 | 1 | fixed | H4×1 | — | 1 | 加蒙层，非品牌令牌 |
| P12 | 1 | needs_human | H4×1 | — | 0 | 品牌色对比度，已升级 |
| P31 | 1 | 残留 | H2×1 | — | 0 | 内容超量，需淬言压条 |
```

收工时这份表直接进《精修报告》，不用重新整理。

## 七、渲染次数怎么控

渲染是这套流程最贵的一步。省的办法：

1. **先跑静态检查**（`svg_quality_checker.py`），它不用渲染，能挡掉一批问题
2. **只渲染要复核的页**：`visual_review.py --pages 03,07,12`
3. **只在改完后渲染**，不要边改边渲染
4. **同一页在本次会话内只渲染最后版本**——中间版本不用留图，除非要做前后对比

前后对比图是 L2 的必需产物，这个不能省。但 L1 不需要对比图，只要清单。

---

## 八、一句话总结

**改得少、退得快、停得住。**

- 改得少：一页 2–4 处，改到 8 处那页就不是原来的设计了
- 退得快：一发现引入新问题立刻回滚，不要试图"再修一下把它救回来"
- 停得住：2 轮封顶，修不动就写清原因交给人
