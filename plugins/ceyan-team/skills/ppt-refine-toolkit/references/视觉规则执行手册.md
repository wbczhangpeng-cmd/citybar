# 视觉规则执行手册

> 这是琢磨的操作主线。每次开工先读这一份。
> 判据的唯一来源是 ppt-master 的 `visual-review.md`（下称"规则原文"）。本手册给你**执行顺序、判据索引、和规则不覆盖的两层扩展**，不重写判据。

---

## 一、规则原文在哪

```
~/.workbuddy/skills/ppt-master/references/visual-review.md
```

配套脚本（均在 **ppt-master 安装目录的 `scripts/`** 下，不是本包文件）：

| 脚本 | 用途 | 什么时候跑 |
|---|---|---|
| `svg_quality_checker.py` | 静态检查：字号锚点漂移、ID 唯一性、XML 合法性、画布与 spec_lock 比对 | **先跑**，不过就不要进视觉复核 |
| `visual_review.py` | 逐页渲染 PNG 到 `<project>/.preview/` | 静态检查过了之后 |
| `svg_to_pptx.py` | 导出原生 pptx | 改完 SVGs 之后 |
| `beautify_identity.py` | 读源 pptx 的画布比例 | 段二接手时用来核对画布 |

**执行顺序不能乱**：静态检查 → 渲染 → 视觉复核 → 导出。反过来会在渲染阶段浪费大量时间，最后被静态检查打回。

## 二、判据索引（只给编号和触发条件，判定细则以原文为准）

### 硬规则（必须修）

| # | 触发 |
|---|---|
| H1 | 元素超出画布 |
| H2 | 文字超出其容器 |
| H3 | 两个文本块重叠 |
| H4 | 对比度不足（小字 < 4.5，24px 以上 < 3.0），或文字压在复杂图上无蒙层 |
| H6 | 元素碰撞且层级违背语义 |
| H7 | 规则声明的页码/页眉/页脚被压、缺失或出界 |
| H8 | 图片渲染坏、变形严重 |
| H9 | 规则声明必需的元素缺失 |

> H5（字号阶梯漂移）由静态检查覆盖，**不要重复查**。

**H4 有一条特殊处理必须记住**：如果涉事前景色或背景色是 `spec_lock` 里的品牌令牌，**不许在页上修**——因为同一个令牌会在所有用到它的页上重复违规，这是品牌级决定。记录下来升级给人，一句话写清「建议全篇把正文色从 #6E7681 提到 #8B949E」这类可执行方案。

### 软规则（明显才动）

| # | 触发 |
|---|---|
| S1 | 同一文本块内行距 < 1.05 倍字号 |
| S2 | 同一文本块内非装饰留白 > 150px |
| S3 | 主标题/英雄块偏离规则声明的锚点 |
| S4 | 同列 x 或同行基线差 > 4px |
| S5 | N 卡横排，相邻间距偏差 > 平均值 5% |
| S6 | 中文字距 / 字号 > 5% |
| S7 | 多个无语义角色的装饰色互相抢 |
| S8 | 最醒目的元素 ≠ 规则声明的主视觉 |
| S9 | 图注离图 > 60px；文字压在杂图上无蒙层；图明显无用途 |
| S10 | `breathing` 页出现 ≥3 个圆角卡片 |

**软规则的核心纪律是「拿不准就不动」。** 少改比改坏好——软规则改错会引入新的硬伤，而用户往往看不出来，只会在评审现场觉得"哪儿不对劲"。

### 禁改清单（§3，和硬规则同等重要）

- **品牌决策**：色令牌、字体族、几何风格
- **版式结构**：列数、图表类型、分节
- **内容**：不增、不删、不改写任何文案（只允许位置、字号在角色锚点 ±2px 内、间距、字距、对齐、蒙层）
- **其他文件**：`design_spec.md`、`spec_lock.md`、`animations.json`、`image_prompts.json`、`images/`、其他页的 SVG
- **原子性**：一处修改一次操作，不许批量替换多个元素

认为某处"违规"但需要重新解释 `design_spec` → **判 `needs_human` 并给一行建议**，不动手。

## 三、扩展层一：通篇一致性

规则原文只管单页，跨页问题它标 `deck_wide` 交给人。**这一手你接。**

### 查什么

| 项 | 具体表现 | 严重度 |
|---|---|---|
| **字号越阶** | 全篇出现 7 种以上字号；或某个字号只在一页出现（说明是临时凑的） | 高 |
| **配色越令牌** | 出现令牌外的颜色；或辅助色被当主色用 | 高 |
| **页码/页眉漂移** | 同类页的页码差 > 2px；有的页有页脚有的没有 | 高（最显廉价） |
| **同类页元素不同位** | 章节扉页的标题，第 2 章在 y=320，第 3 章在 y=360 | 高 |
| **页型分布异常** | 论点支持页占比 < 30%（说明论证碎）或图表页 > 30%（说明在用图代替论证） | 中 |
| **视觉重心无起伏** | 连续 5 页以上视觉密度相同——听众会疲劳 | 中 |
| **章节扉页节奏** | 有的章节有扉页有的没有 | 中 |

### 怎么判

**用脚本，不要用眼睛。** 45 页靠扫必漏，而且漏的往往是最要命的那几项（页码差 4px，你在缩略图上看不出来，投影到大屏上就是歪的）。

```bash
python scripts/check_deck_consistency.py "<定稿.pptx>"
python scripts/check_deck_consistency.py "<定稿.pptx>" --tokens tokens.json
```

### deck_wide 的处理规则

同一问题在多页重复 → **这是全篇决定，不是单页修补**：

1. 别逐页改。逐页改必漏，而且改到第 12 页你会忘了第 3 页用的什么值
2. 提一个**全篇统一方案**（「全篇 47 处正文色统一到 #6E7681」而不是「P3 改色」）
3. 走 **L2** 报给用户，一次批准、一次执行

## 四、扩展层二：表达强化

规则原文只判断「这页是否与 spec 声明一致」，不判断「这页能不能说服人」。**只在重点页做。**

### 四个判断

1. **主视觉是否承载核心结论**
   最醒目的那个元素，是不是这页要说的那句话？常见病：图片最抢眼，结论句缩在角落。听众的眼睛先落在图上，然后就没有然后了。

2. **阅读动线是否顺**
   人看页面是有顺序的：左上 → 右下。如果关键信息在右下角而左上角放了一个大装饰，动线就断了。

3. **图文是否各说各话**
   图在讲 A，文字在讲 B，两者只是被放在了同一页上。判断法：把文字遮住，只看图能否推出结论；把图遮住，只看文字能否推出结论。都不行就是各说各话。

4. **页面是否"平"**
   干净、正确、无硬伤，但没有任何东西让人多看一眼。根源通常是**构图**不是字距——所有元素均匀分布、大小相近、没有主次。这种页只能靠调分区比例（L2）救，改字距没用。

### 强化手段（按代价从低到高）

| 手段 | 级别 | 说明 |
|---|---|---|
| 调整强调对象的大小/字重差 | L1（在角色锚点内） | 最便宜，往往够用 |
| 加/减留白，收紧同一组元素 | L1 | 让分组关系一眼可见 |
| 调强调层级（哪句放大、哪句降级） | L2 | 需要用户确认，因为会影响他想讲的重点 |
| 调分区比例 | L2 | 救"平"的主要手段 |
| 换版式变体 | L2 | 版式库内换，不新造 |
| 删装饰 | L2 | 装饰是最容易过量的东西 |

**尺度**：一页改 2–4 处就够。改到 8 处，那页已经不是原来的设计了，用户认不出来。

## 五、渲染与复核的执行细节

### 渲染

```bash
# 起预览服务（渲染器从 live_preview/lock.json 发现端口）
python skills/ppt-master/scripts/svg_editor/server.py <project_path> --no-browser

# 渲染全部页
python skills/ppt-master/scripts/visual_review.py <project_path>

# 只渲染指定页
python skills/ppt-master/scripts/visual_review.py <project_path> --pages 03,07,12
```

**必须用 playwright + chromium，不能用 cairosvg。** cairo 没有字体回退链，中文会渲染成方块（豆腐块），你会以为全篇崩了，实际只是渲染器不对。

### 渲染失败的处理

只对 `"ok": true` 且 `"all_background": false` 且画布信息完整的页做复核。其余：

- **退出码 2 或 3** → 停止派发，先修渲染
- **退出码 4** → 可复核成功的那部分，但**必须**把失败页重试或明确交给人，不能漏
- 空白画面通常是 `<use>` 引用断了或图片资源缺失

### 一批多大

| 场景 | 批大小 |
|---|---|
| 45 页常规精修 | 10 页/批（省 token） |
| 高精度短稿（≤15 页） | 3 页/批 |
| 单页深磨 | 1 页 |

同一页**第二次复核前必须重新渲染**——不重渲染等于在验旧图。

### 备份纪律

每页第一次编辑前：

```
cp <project>/svg_output/<page>.svg <project>/.review/backup/<page>.iter<N>.svg
```

备份路径写进每条 finding。**没有备份不许改**——回滚靠它。

## 六、一页改完，怎么算过

```
硬伤 0 条
软问题 ≤ 1 条（且已记录在 untouched_concerns）
可编辑性合格
未被验证引入新问题（第 2 轮时）
```

四条全过 = `fixed`/`ok`。任何一条不过 = `needs_human` 或进残留。

**"还能再改改"不算不过。** 精修的终点是「没有明确缺陷」，不是「改到我觉得满意」。后者没有终点，而且会把你认为的审美偏好强加给用户。

## 七、常见事故与对策

| 事故 | 原因 | 对策 |
|---|---|---|
| 改完 A 页，B 页字体变了 | 动了共享样式或 `spec_lock` | 只改页内元素；`spec_lock` 只读 |
| 整页看起来歪了但说不出哪歪 | 页眉基线差 4px | 跑一致性脚本，别靠眼睛 |
| 修了溢出，那页变成一张图 | 图省事 | 硬禁令：文字必须原生。回滚 |
| 改到第 3 轮还在动 | 软规则震荡 | 立即停，判 `needs_human`，写清两个修法在互相打架 |
| 用户说"还不如原来" | 改太多，动了设计意图 | 从备份回滚整页，重来只改硬伤 |
| 46 页改完发现 P7 忘了 | 没有逐页台账 | 用报告模板的逐页状态表，边改边填 |

## 八、和上游的边界（再强调一次）

| 发现 | 交给谁 | 说什么 |
|---|---|---|
| 视觉规范本身排不出来 | **立象** | 哪条规则、哪个页型、冲突在哪 |
| 文案读不通、术语用错 | **淬言** | 哪一页哪一句 |
| 数字对不上、结论站不住 | **筑策 / 验筹** | 哪两处打架 |
| 页序、章节结构有问题 | **析纲** | 哪两页该合并 |

**你改得动，不等于你该改。** 改完之后上游不知道，下一轮谁改谁覆盖，最后没人说得清哪个版本是真的。
