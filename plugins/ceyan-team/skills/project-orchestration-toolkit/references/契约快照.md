## 三、流程骨架（7 步 + 1 中心）

```
① 筑策 总体策划定位
② 验筹 商业逻辑审查
③ 析纲 出 PPT 框架
④ 淬言 文字润色去 AI 味
⑤ 立象 视觉表达设计
⑥ 落版 生成初稿
⑦ 琢磨 精修定稿
→ 交付
```

**闸门位置**：每两个相邻步骤之间 = 一道闸（共 7 道，含开工前的闸门零）。判据见 `闸门判据表.md`。

---

## 四、几条会跨专家生效的事实（变更时须同步本工具）

| 事实 | 来源 | 若变更的影响 |
|---|---|---|
| 验筹产出《事实黑名单》，是后续所有步骤的硬约束 | 验筹包 | 闸门二、三、四都要改 |
| 析纲的「表达方式」不含「强调层级」，由淬言补 | 析纲 → 淬言 | 闸门三、四要改 |
| 立象把沟通契约写入 `design_spec §I` 并禁止 Strategist 重复发问 | 立象包 | 闸门五要改 |
| 落版必须交出项目工作区路径（`svg_output/` + spec + lock + images） | 落版包 | 闸门六、七要改，琢磨能力降级 |
| 琢磨用 append 方式接手新增页，不用 roundtrip | 琢磨包 | 闸门七要改 |
| 可编辑性是放行条件（全篇零不合格） | 落版 + 琢磨 | 闸门六、七要改 |

## 六、升级时的核对流程

1. 读各专家 `agents/*.md` 的 frontmatter 与「闸门/交接」相关章节
2. 对照 `专家接口速查.md` 逐项核对输入输出是否有变
3. 对照 `闸门判据表.md` 逐条核对判据是否仍然成立
4. 有差异 → 更新这两个文件 + 本快照，并在版本号上体现
5. 无差异 → 只更新本快照的核对时间
