# 契约快照

你是照着别人的房子改装修，所以**门框尺寸必须按人家的来**。这份文件记录你依据的契约，以及升级时怎么比对。

## 二、项目级 Design Spec 结构

文件名：`<项目路径>/design_spec.md`
首行必须是：`<!-- ppt-master-schema: design-spec/v1 -->`
第二行：`# <项目名> - Design Spec`

| 章节 | 内容 | 你需要写吗 |
|---|---|---|
| **§I Project Information** | 项目名 / 画布 / 页数 / 语言 / 受众 / 沟通意图 / 期望效果 / 核心信息 / 交付场景 / 后续用途 / 阅读模式 / 内容策略 / 设计风格 / 生成模式 / 备注开关 / 日期 | **是**（受众与意图直接用已确认值） |
| **§II Canvas Specification** | 格式 / 尺寸 / viewBox / 边距 / 内容区 | 是 |
| **§III Visual Theme** | Mode / Visual style / Theme / Tone；**Color Scheme 表（角色·HEX·用途）** | **是（核心）** |
| **§IV Typography System** | 字族、字号阶梯、字重、行高 | **是（核心）** |
| **§V Layout Principles** | 栅格、分区、边距、密度 | **是（核心）** |
| **§VI Icon Usage Specification** | 图标库选型与使用规则 | 是（若用图标） |
| **§VII Visualization Reference List** | 图表与表格的目录引用 | 是（有图表引用时；无则整节删除，不保留空标题） |
| **§VIII Image Resource List** | 图片资源清单 | 是（对应你的图片需求清单） |
| **§IX Content Outline** | 逐页清单（页序 + 每页内容块） | **是（你的逐页蓝图落在这里）** |
| **§X Speaker Notes Requirements** | 演讲备注要求 | 是（交演讲备注的语体规定给下游） |

**关键映射**：
- 你的**设计令牌** → §III + §IV + §V + §VI
- 你的**逐页蓝图** → §IX Content Outline（图表的形态与映射写进 §VII 的引用 + §IX 的页面块）
- 你的**图片需求清单** → §VIII Image Resource List

## 三、Style 模板工作区结构

```
templates/styles/<style_id>/
└── templates/
    └── design_spec.md      # style 类 spec
```
索引：`templates/styles/styles_index.json`（键为 `style_id`，值含 `summary` 与 `keywords`）

Style spec 的 frontmatter：
```yaml
---
style_id: <kebab-case>
kind: style
summary: <一句话>
keywords: [<5 个左右>]
---
```

Style spec 的正文结构（与你的《风格总结》高度重合）：
| 章节 | 对应你的 |
|---|---|
| I. Style Overview | 一句话定位 + 关键词 + 适用场景 |
| II. Communication Method | 论证方式与纪律（与页型偏好相关） |
| III. Page Role Vocabulary | **逐条对应你的 15 种页型**（角色·沟通任务·证据义务·构图倾向） |
| IV. Evidence & Data Expression | 图表/表格/来源/可编辑性 |
| V. Visual System Defaults | 色彩行为、构成、密度、装饰、字体性格 |
| Fallback Color Scheme | 角色·HEX·用途表 |

**注意**：Style 只拥有"方法与视觉默认值"，**不拥有**品牌标识、页面结构（那是 Layout/Deck 的）、也不拥有当前项目的具体应用。所以：
- 你提取出的"通用风格"→ 存为 Style
- 你为本项目定的一次性方案 → 写进项目 `design_spec`，不要污染 Style

## 五、一条硬约束（最容易出错的地方）

ppt-master 的 Strategist 会重新追问**受众、沟通意图、期望效果、核心信息**。这些在前四步已经确认过了。

**你必须做的事**：把已确认的沟通契约逐项写进 §I，并加一行明确声明：

> `Template Application: 沟通契约已由上游确认，禁止 Strategist 重复发问；如需澄清，以本节为准。`

不加这一行，下游会把前面几轮的确认全部推翻重来，用户会觉得"怎么又问一遍"。

## 六、可编辑性在契约里的位置

Style spec 的 "IV. Evidence & Data Expression" 里有 **Native Editability** 一项：优先使用可编辑的原生图表、表格与形状；否则宁可保留一个可读的可编辑形状化表示，也不牺牲可编辑性。

**这与你第九节的"可编辑性契约"方向一致**，写的时候直接对齐：
- 文字 → 原生文本框
- 表格/图表 → 优先原生对象
- 复杂关系图 → 原生形状拼，不整体截图
- 图片 → 只用于照片/意向图/图纸，不承载文字

并在 §IX 的页面块里为每种页型标注"可编辑边界"。

## 七、校验与排查

- 结构错 → 对 `design_spec.schema.json` 校验
- 首行缺 schema 声明 → 必然解析失败
- §VII 无图表引用却留了空章节 → 删掉整节（含标题）
- 字段写了占位符/示例值 → 视为未完成，必须填实
